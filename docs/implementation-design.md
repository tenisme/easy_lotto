# Easy Lotto 구현 설계 초안

> 작성일: 2026-11-01 · 기준: `product-spec.md` 0.12, `wireframes.md`, `storage-wireframes.md`

이 문서는 화면, 추천 규칙, 로컬 저장소를 연결하는 구현 계약이다. UI 디자인 세부사항은 각 와이어프레임 문서를 따른다. 현재 Flutter 코드는 기본 예제 화면만 있으므로 아래 순서대로 기능을 수직으로 연결한다.

## 1. 첫 구현 범위와 순서

1. 순수 Dart 모델과 추천 엔진: 번호 1~45, 6개 게임, 규칙 검증, 고유 1~5게임 생성. 외부 회차 데이터는 주입 가능한 인터페이스로 받는다.
2. 로컬 저장소: 설정, 내 번호, 저장한 조합, 복권 용지와 게임 스냅샷, 보기 스타일.
3. 추천 홈 → 상세 설정 → 결과: 임시 설정과 저장 설정, 재생성 확인, 개별 숫자·조합 저장.
4. 보관함 → 용지 만들기·편집 → 번호 크게 보기: 네 경로로 조합 추가, 용지 스냅샷, 디자인 적용.
5. 권한·출처가 확인된 후 추첨 데이터 동기화 어댑터 연결. 그전에는 회차 기반 두 옵션을 실제 배포 화면에서 비활성화하고 엔진 테스트에만 고정 시험 데이터를 사용한다.

선택지 사용 비율 분석은 1차 구현의 필수 종속 기능으로 두지 않는다. 사용자 데이터 원격 수집 없이 로컬 기능을 완성할 수 있다.

## 2. 도메인 모델

- `LottoGame`: 오름차순의 서로 다른 정수 6개. 생성 시 1~45 범위와 중복을 검증한다. 동일성은 정렬된 6개 숫자로 비교한다.
- `RecommendationOptions`: 고정수·제외수, 홀짝, 고저, 총합, 연속 묶음, 직전 회차 제외, 미출현 기간·범위·포함 수. 스키마 버전을 함께 직렬화한다.
- `GenerationRequest`: 옵션, 게임 수(1~5), 검증된 추첨 데이터 스냅샷, 제외할 기존 게임 집합. 조합 추가에서는 게임 수를 항상 1로 둔다.
- `GenerationResult`: 게임 목록, 사용한 옵션 스냅샷, 추첨 데이터 기준 회차, 생성 출처(`random` 또는 `configured`).
- `RecommendationPreset`: ID, 이름, 옵션, 생성·수정 시각. 편집 중인 값은 저장 전까지 별도 초안으로 유지한다.
- `SavedNumberSet`: 사용자가 보관함에 명시적으로 저장한 게임. 생성 출처와 옵션 스냅샷을 보유한다.
- `LotteryPaper`: 이름, 1~5개 `PaperGame`, 용지별 디자인 재정의 값. `PaperGame`은 번호 6개를 복사해 보관하며 원본 조합 ID는 선택적 출처 정보다.

`내 번호`의 하트 저장, 조합 저장, 복권 용지 추가는 서로 다른 동작이다. 용지에 추가해도 `SavedNumberSet`을 자동 생성하지 않는다.

## 3. 화면 상태와 이동

| 화면 | 유지할 상태 | 주요 이동·저장 |
|---|---|---|
| 추천 홈 | 게임 수, 완전 랜덤/상세 설정, 선택한 저장 설정 ID | 저장 설정이 없으면 `설정 만들기`; 있으면 선택 후 `설정 수정` 또는 `번호 생성` |
| 상세 설정 | 저장된 원본과 분리된 편집 초안, 진입 출처 | `설정 저장`은 현 화면 유지; `번호 생성`은 현재 초안으로 결과 생성 |
| 추천 결과 | 생성 당시 설정 스냅샷, 현재 미저장 게임, 저장 여부, 임시 설정 여부 | 뒤로가기는 추천 홈; `설정 수정`은 결과 유지; `다시 생성`은 미저장 결과 교체 확인; `복권 용지에 저장`은 용지 선택·생성 |
| 조합 추가 | 출처 카드 4개 중 선택, 현재 미리보기 게임, 상세 설정 초안 | 직접 선택·내 번호·완전 랜덤·상세 설정으로 1게임 완성; `복권 용지에 추가` |
| 용지 편집 | 용지의 게임 1~5개와 순서, 아직 확정하지 않은 교체 후보 | 새 조합은 용지에 직접 추가; 기존 게임 교체는 전후 비교 후 확정 |
| 번호 크게 보기 | 용지 ID, 이번 진입에 적용된 디자인 ID | 최초 진입 뒤 안내 팝업 표시; `보기 스타일` 또는 `용지 편집` |

결과 화면의 `다시 생성`은 저장되지 않은 현재 결과를 없애므로 기존 확인 문구를 사용한다. 조합 추가 화면의 `다시 생성`은 아직 저장·추가되지 않은 미리보기 1게임만 바꾸므로 확인창 없이 실행한다. 상세 설정 경로에서는 같은 설정으로 다시 생성한다.

화면을 나갈 때는 세션에 남은 미저장 게임과 임시 설정을 각각 확인한다. 이미 `내 번호`, `저장한 조합`, 용지에 기록된 항목은 세션 이탈로 삭제하지 않는다.

## 4. 추천 엔진 계약

엔진은 화면이나 DB에 의존하지 않는다. 검증된 회차 목록을 읽기 전용 입력으로 받아 필요한 집합을 계산한다.

1. 입력 형태와 숫자 범위를 검증한다.
2. 활성화된 회차 기반 옵션에 필요한 검증 데이터가 있는지 검사한다. 범위 선택이 6개면 본번호만, 7개면 보너스도 포함한다.
3. 고정수·제외수·직전 번호 제외를 적용하고 명시적 충돌을 반환한다.
4. 남은 후보에서 6개 조합을 탐색하며 홀짝·고저·총합·연속 묶음·미출현 K개를 모두 만족하는지 판정한다. 연속 묶음은 최대 연속 구간 기준이다.
5. 요청한 수만큼 서로 다른 조합이 가능한지 확인한 뒤 무작위로 고른다. 가능하지 않으면 가능한 고유 게임 수와 관련 규칙을 오류로 반환한다.

반환형은 `Success(games)` 또는 `Failure(issues)`로 고정한다. `issues`는 규칙 코드, 관련 옵션 키, 짧은 사용자 안내를 포함한다. 설정을 조용히 완화하거나 무한 재시도하지 않는다. 난수 공급자를 주입해 테스트를 재현할 수 있게 한다. 작은 후보군에서는 가능한 조합을 직접 열거하고, 큰 후보군은 제약을 이용해 탐색·무작위 선택한다. 표본 추출 방식은 특정 유효 조합에 체계적 편향이 생기지 않는지 별도로 검증한다.

`DrawRepository`는 최신 검증 회차와 최근 N회 목록을 제공한다. 동기화 실패 시 마지막 검증 데이터를 반환하고, 필요한 데이터가 없으면 회차 기반 옵션만 사용할 수 없다고 알린다. 개발용 고정 데이터는 테스트에만 둔다.

## 5. 로컬 저장 계약

SQLite 마이그레이션 1부터 테이블을 만든다. 모든 날짜는 UTC ISO 8601로 저장하고 화면에서 지역 시간으로 표시한다. 여러 행을 동시에 바꾸는 저장은 트랜잭션으로 처리한다.

| 테이블 | 키·제약 | 역할 |
|---|---|---|
| `recommendation_presets` | `id` PK, `name` UNIQUE | 설정 JSON과 버전 저장 |
| `favorite_numbers` | `number` PK, 1~45 CHECK | 개별 숫자 저장 |
| `number_sets` + `number_set_items` | 세트 ID PK, `(set_id, number)` PK | 명시적으로 저장한 조합만 기록 |
| `lottery_papers` | `id` PK | 이름·용지별 디자인 재정의 |
| `lottery_paper_games` | `id` PK, `(paper_id, position)` UNIQUE, position 0~4 CHECK | 용지 안의 게임; `source_set_id`는 NULL 가능 |
| `lottery_paper_game_items` | `(paper_game_id, number)` PK | 용지 번호 스냅샷 |
| `display_preferences` | 단일 행 | 전역 기본 디자인·적용 방식; 랜덤 전환에도 기존 값 보존 |
| `draw_results` + `draw_result_main_numbers` | 회차 PK, `(round, number)` PK | 검증된 회차의 본번호와 보너스 보관 |

한 게임이 정확히 6개인지, 용지가 1~5게임인지, 동일 저장 조합 중복 여부는 저장 서비스의 트랜잭션에서 검증한다. 단일 행의 CHECK 제약만으로 자식 행 개수를 보장할 수 없기 때문이다. 저장 조합 삭제 시 용지 스냅샷을 유지하고 `source_set_id`만 NULL로 만든다. 용지 게임 번호는 변경되지 않는다.

보기 스타일 적용 우선순위: 랜덤 모드면 화면 진입 시 한 디자인을 뽑아 유지한다. 용지별 모드면 용지 재정의 값, 없으면 전역 기본값을 사용한다. 기본 모드면 모든 용지에 전역 기본값을 사용한다.

## 6. 추천 결과에서 용지에 담을 게임 선택

`복권 용지에 저장`을 누르면 생성된 모든 게임을 기본 선택한 선택 화면을 연다. 사용자는 게임별로 선택을 해제할 수 있다. 최소 1개는 선택해야 계속할 수 있으며, 선택한 게임만 용지 선택·생성 화면으로 넘긴다. 기존 용지의 남은 칸보다 선택한 게임이 많으면 저장을 진행하지 않고 선택 게임을 줄이거나 다른 용지 또는 새 용지를 선택하도록 안내한다. 용지에 넣은 게임은 번호 스냅샷으로 보존하며 `저장한 조합`에는 자동 추가하지 않는다.

## 7. 동행복권 회신 반영 상태

사용자가 옮겨 적은 동행복권 회신에 따르면 역대·최신 회차와 당첨 인원·금액·판매점 정보까지 출처 표기 조건으로 상업적으로 활용할 수 있다. 첫 구현에서는 회차·추첨일·본번호 6개·보너스 번호만 수집한다. 회차별 결과 주소가 작동한다는 사용자 확인을 토대로, 초기 역대 결과를 적재한 후 저장된 마지막 회차의 다음 회차를 주 1회 조회한다. 최신 전용 주소는 필수가 아니다. 정상 결과·미추첨·사이트 오류를 구분하고 검증 실패 시 마지막 정상 데이터를 유지한다. 화면에는 `출처 : 동행복권`을 표시하고 `동행복권` 텍스트가 공식 메인 사이트를 시스템 브라우저에서 열도록 한다.

기존 기획서의 `lottery_paper_games`에는 `id PRIMARY KEY`와 `(paper_id, position) PRIMARY KEY`가 함께 적혀 있었다. SQLite에는 기본키를 하나만 둘 수 있으므로 이 문서처럼 `id` 기본키와 위치 고유 제약으로 구현한다.
