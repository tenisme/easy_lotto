## 2026-11-02 동행복권 회신 관련 업데이트

사용자가 동행복권 회신에서 옮겨 적은 조건은 다음과 같다. 원문은 공유할 수 없으므로 아래 내용은 사용자 전달 사항으로 기록한다. 아래 2026-10-26 조사 결과의 `허가 미확인` 판정은 이 회신을 받기 전의 기록이다.

- 수집 범위: 역대·최신 회차 당첨 기록, 회차별 당첨 등위의 인원·금액, 자동·수동 당첨 인원, 당첨 복권 판매점 이름·주소
- 활용 범위: 출처를 명확하게 표기하면 상업적 이용 가능
- 출처 표기: `출처 : 동행 복권` 또는 동행 복권 로고 이미지
- 조회 경로: 동행복권 웹페이지 또는 공개된 API 중 선택
- 조회 빈도: 필요한 데이터만 주 1회 가져가는 방식에 문제가 없다는 취지

이 내용이면 제품의 데이터 출처와 수집 범위를 정하는 데 충분하다. 아직 특정 API 주소, 응답 형식, 웹페이지에서의 추출 방식은 정해지지 않았으므로 연동 전에 기술적으로 확인한다. 첫 구현에는 회차·추첨일·본번호 6개·보너스 번호만 필요하다. 당첨 인원·금액·판매점 정보는 사용 기능이 정해질 때 수집한다. 출처는 우선 허용된 텍스트 문구로 표기한다. 초기 전체 회차를 앱 파일에 포함하거나 자체 서버로 다시 배포하는 방식은 별도 배포 설계에서 범위를 검토한다.

## 2026-11-02 조회 주소 재확인

- 공식 결과 화면: <https://www.dhlottery.co.kr/lt645/result>
- 결과 화면의 내부 조회 주소 후보: `https://www.dhlottery.co.kr/lt645/selectPstLt645InfoNew.do` (최신 결과), `https://www.dhlottery.co.kr/lt645/selectPstLt645Info.do?srchDir=center&srchLtEpsd={회차}` (회차별 결과). 두 번째 형식은 [제삼자의 2026년 페이지 관찰 기록](https://linenim.tistory.com/entry/%EB%8F%99%ED%96%89%EB%B3%B5%EA%B6%8C-%EB%A1%9C%EB%98%90-%ED%9A%8C%EC%B0%A8%EB%B3%84-%EB%8B%B9%EC%B2%A8%EB%B2%88%ED%98%B8-%EC%A1%B0%ED%9A%8C-%EB%B0%8F-%EC%97%91%EC%85%85-VBA-%EB%8B%A4%EC%9A%B4%EB%A1%9C%EB%93%9C)에 근거한다.
- 위 주소는 페이지 내부에서 사용하는 것으로 알려진 경로이며, 문서화된 공식 공개 API라는 증거는 찾지 못했다. 공식 결과 페이지 요청은 이 조사 환경에서 `/error.html`로 전환됐지만 회차별 JSON 주소는 별도 요청으로 응답을 확인했다. 실제 연동 전 최신/미추첨 회차의 동작도 확인한다.
- 앱의 출처 표기는 `출처 : ` 뒤의 `동행복권`만 누를 수 있는 텍스트로 만들고 공식 메인 <https://www.dhlottery.co.kr/>로 연결한다. 링크를 누르면 시스템 브라우저로 열며, 스크린 리더에도 `동행복권 홈페이지 열기`로 읽히게 한다.

### 회차별 주소만으로 갱신하는 방법

사용자가 `.../selectPstLt645Info.do?srchDir=center&srchLtEpsd=5` 주소에서 5회차 결과가 표시되는 것을 확인했다. 2026-11-02 조사 환경에서도 같은 주소가 HTTP 200, `application/json;charset=UTF-8`로 응답했다. 응답의 `data.list[0]`에는 `ltEpsd=5`, `ltRflYmd=20030104`, 본번호 `tm1WnNo`~`tm6WnNo`(16, 24, 29, 40, 41, 42), 보너스 `bnsWnNo=3`이 있었다. 최신 전용 주소가 없어도 회차별 주소만으로 번호 규칙에 필요한 데이터는 얻을 수 있다.

1. 공식 역대 결과 다운로드로 초기 회차·추첨일·본번호 6개·보너스 번호를 한 번 적재하고, 누락·중복·번호 범위를 검증한다.
2. 매주 저장된 최대 회차 `R`의 다음 회차 `R+1`을 조회한다. 유효한 새 결과가 나오면 검증 후 저장하고, 필요하면 이어지는 누락 회차만 조회한다.
3. `R+1` 결과가 아직 없으면 기존 DB를 유지하고 다음 주기를 기다린다. 차단·오류 화면, 빈 응답, 형식 변경은 미추첨 응답으로 단정하지 않고 오류로 기록한다.

따라서 최신 전용 주소의 발견은 1차 연동의 선행 조건이 아니다. 5회차 응답 형식은 확인했지만 미추첨 회차 응답과 최신 회차의 동작은 아직 확인하지 않았다. 실제 파서는 성공 응답의 회차 일치와 필드 유효성을 검사하고 HTML 오류 페이지나 비정상 JSON을 정상 데이터로 저장하지 않는다.

## 1. 결론 요약

직전 회차 번호와 미출현 번호 기능을 1차 출시에 포함하는 것은 기술적으로 가능하다. 다만 현재 확인한 출처 중 별도 확인 없이 프로덕션 앱에서 바로 사용할 수 있는 출처는 없다.

- 동행복권 공식 사이트에는 현재 회차 데이터를 반환하는 내부 JSON 요청이 있다.
- 해당 요청은 공개 API 문서, 사용 신청 절차와 호출 한도가 확인되지 않은 웹사이트 내부 인터페이스다.
- 동행복권 현행 사이트 이용약관은 특정 기능을 반복적 또는 규칙적으로 호출하는 행위를 금지한다.
- 공공데이터포털에서는 로또 6/45 회차별 본번호·보너스 데이터 API를 찾지 못했다. 확인된 관련 데이터는 1등 당첨 판매점 현황이었다.
- `smok95/lotto`는 사용하기 편한 정적 JSON을 제공하지만 오류 가능성을 고지하고 있으며 저장소에 라이선스가 없다.

따라서 권장안은 **데이터 이용 허가가 확인된 출처 → Easy Lotto가 관리하는 정적 배포 피드 → 앱의 검증된 로컬 DB** 구조다. 허가가 확정되기 전에는 외부 데이터 기능을 구현하되 기능 플래그로 비활성화할 수 있게 한다.

## 2. 조사 범위와 판정 기준

다음 항목을 기준으로 출처를 평가했다.

1. 본번호 6개, 보너스 번호, 회차와 추첨일 제공 여부
2. 전체 과거 회차와 최신 회차 접근 가능 여부
3. 공개 API 또는 재사용 허가의 명확성
4. 응답 형식과 스키마의 안정성
5. 호출 제한과 장애 대응 가능성
6. 앱에서 직접 호출할 때의 확장성
7. 오프라인용 초기 데이터로 재배포할 수 있는지
8. 오류 또는 변조를 검증할 수 있는지

법률 자문을 수행한 것은 아니며, 이용 권한이 불명확한 경우 권리자에게 서면 확인하는 것을 출시 조건으로 삼는다.

- 응답에는 회차, 본번호 6개, 보너스, 추첨일과 당첨 정보가 포함된다.

과거 널리 사용되던 `common.do?method=getLottoNumber` 주소는 조사 시 JSON 대신 사이트 HTML을 반환해 기존 연동 방식과 호환되지 않았다.

#### 이용 조건

현재 사이트 이용약관:

- <https://www.dhlottery.co.kr/trms/home>
- 게시일: 2025-07-15
- 시행일: 2025-07-29

약관 제12조 제1항의 금지행위에는 다음 내용이 포함되어 있다.

- 회사가 제공하는 이용방법에 의하지 않은 비정상적인 서비스 이용 또는 시스템 접근
- 회사 및 제3자의 지식재산권 침해
- 특정 기능을 반복적 또는 규칙적으로 호출하는 행위

내부 JSON 주소는 공개 API로 문서화되어 있지 않다. 앱 설치 단말마다 정기 호출하는 구조는 약관상 위험이 있고, 주소와 스키마가 예고 없이 변경될 수 있다.

#### 판정

**프로덕션 직접 호출 비권장**

- 정확성 확인용 공식 기준 출처로는 유용하다.
- 개발 중 제한된 수동 표본 확인에는 사용할 수 있다.
- 자동 수집, 앱 직접 호출 또는 데이터 재배포는 동행복권의 서면 확인 전까지 확정하지 않는다.

### 3.3 `smok95/lotto` 정적 JSON

출처:

- 저장소: <https://github.com/smok95/lotto>
- 최신 회차: <https://smok95.github.io/lotto/results/latest.json>
- 전체 회차: <https://smok95.github.io/lotto/results/all.json>
- 회차별: `https://smok95.github.io/lotto/results/{회차}.json`

#### 기술적 장점

- GitHub Pages 기반 정적 JSON이다.
- `Access-Control-Allow-Origin: *` 헤더를 제공한다.
- 최신, 전체, 회차별 조회 형식이 단순하다.
- 2026-10-24 기준 제1회부터 제1247회까지 1,247개 연속 회차가 있었다.
- 전체 데이터에서 다음 기본 검증을 수행했고 위반 레코드는 없었다.
  - 본번호 정확히 6개
  - 모든 번호 1~45
  - 본번호 중복 없음
  - 보너스가 본번호와 중복되지 않음
  - 회차 번호 1~1247 연속
- 최신 제1247회 데이터는 조사한 동행복권 공식 응답 표본과 일치했다.

#### 위험

- README는 정보에 오류가 있을 수 있다고 명시한다.
- 저장소에 LICENSE 파일이나 GitHub 라이선스 선언이 없다.
- 저장소의 `policy.html`은 `치와와`라는 서비스의 개인정보 처리 목적, 보유 기간과 개인정보 보호책임자 등을 적은 개인정보처리방침이다. 로또 JSON의 저작권, API 이용, 상업적 사용 또는 재배포를 허용하는 라이선스 문서가 아니다.
- 데이터 수집 출처와 자동 갱신 방식이 문서화되어 있지 않다.
- 운영 지속성, 정정 절차와 서비스 수준 보장이 없다.
- 라이선스가 없으므로 저장소 내용의 복제·수정·재배포 권한을 가정할 수 없다.

#### 판정

**조건부 후보**

저장소 운영자가 앱 사용과 초기 데이터 재배포를 명시적으로 허용하거나 적절한 라이선스를 추가한 경우 보조 출처로 검토할 수 있다. 허가 전에는 프로덕션 의존성과 앱 번들 데이터의 원천으로 사용하지 않는다.

### 3.4 자체 관리 정적 피드

Easy Lotto가 관리하는 HTTPS 정적 저장소에 검증된 데이터만 배포하는 방식이다.

#### 장점

- 설치된 앱이 동행복권 내부 주소를 직접 호출하지 않는다.
- 앱과 외부 사이트의 스키마를 분리할 수 있다.
- 출처가 변경되어도 앱 업데이트 없이 수집 계층만 변경할 수 있다.
- ETag, 캐시와 작은 증분 파일을 사용할 수 있다.
- 정적 호스팅을 사용하면 서버 실행 비용과 공격 표면이 작다.

#### 전제

- 원천 데이터의 수집·저장·재배포 권한이 먼저 확인되어야 한다.
- 자동 수집이 허용되지 않으면 관리자가 공식 결과를 수동 확인해 피드를 갱신해야 한다.
- 갱신 담당, 장애 확인과 정정 절차가 필요하다.

#### 판정

**권한 확인 후 권장하는 배포 구조**

`공개 정보`, `공개 데이터` 또는 `공식 API`라는 표현만으로 이용 허가가 확보되지는 않는다. 출처 표기와 비제휴 고지는 투명성을 높이지만, 원천 데이터의 자동 조회·저장·재배포 권한 확인을 대신하지 않는다.

## 5. 권장 동기화 구조

```text
허가된 원천 데이터
        ↓ 수집 또는 수동 입력
수집기 검증 + 관리자 검토
        ↓
Easy Lotto 정적 피드
  ├─ manifest.json
  ├─ snapshot-vN.json
  └─ updates/{회차}.json
        ↓ HTTPS + ETag
앱 검증 계층
        ↓ SQLite 트랜잭션
로컬 draw_results
        ↓
직전 회차·미출현 번호 규칙
```

### 5.1 초기 데이터

- 출시 시점까지 검증된 전체 회차의 최소 필드만 앱에 포함한다.
- 최소 필드: 회차, 추첨일, 본번호 6개, 보너스 번호
- 당첨금, 당첨자 수와 판매액은 현재 기능에 필요하지 않으므로 포함하지 않는다.
- 앱 번들의 스냅샷 버전과 마지막 회차를 기록한다.
- 초기 데이터의 재배포 권한과 출처 표기를 출시 전에 확정한다.

### 5.2 원격 갱신

- 앱 시작 때마다 호출하지 않고 마지막 확인 후 일정 시간이 지난 경우에만 확인한다.
- 최신 회차 자동 확인은 주 1회를 기본으로 한다. 실제 확인 시점과 실패 후 재시도 정책은 회신 범위에 맞춰 정한다.
- 사용자가 `지금 업데이트`를 선택하더라도 같은 주에 원천 사이트를 다시 조회하지 않고, 마지막으로 저장된 정상 데이터를 표시한다. 자체 캐시를 두는 경우 캐시 조회는 별도로 설계한다.
- `If-None-Match` 또는 `If-Modified-Since`로 변경이 없을 때 본문 다운로드를 피한다.
- 새 회차만 증분으로 내려받고, 여러 회차가 누락됐으면 필요한 범위를 순서대로 채운다.
- 네트워크 실패 시 마지막 정상 DB로 계속 동작한다.
- 백그라운드에서 실패를 무한 재시도하지 않는다.

### 5.3 정정과 롤백

- 기존 회차와 다른 값이 도착하면 자동 덮어쓰지 않는다.
- 원격 manifest에 정정 버전과 변경된 회차를 명시한다.
- 정정 데이터는 별도 검증 후 하나의 SQLite 트랜잭션으로 반영한다.
- 트랜잭션 검증 실패 시 전체 변경을 롤백한다.
- 앱에는 데이터 기준 최신 회차, 마지막 확인 시각과 오류 상태를 표시한다.

## 6. 피드 스키마 초안

### `manifest.json`

```json
{
  "schemaVersion": 1,
  "datasetVersion": "2026-10-24.1",
  "latestDraw": 1247,
  "publishedAt": "2026-10-24T21:30:00+09:00",
  "sourceName": "확정 후 입력",
  "snapshotUrl": "snapshot-v1.json",
  "snapshotSha256": "..."
}
```

### 회차 레코드

```json
{
  "round": 1247,
  "drawDate": "2026-10-24",
  "mainNumbers": [8, 14, 21, 22, 42, 45],
  "bonusNumber": 24
}
```

앱은 알 수 없는 `schemaVersion`을 받으면 데이터를 적용하지 않고 기존 DB를 유지한다.

## 7. 데이터 검증 규칙

### 7.1 레코드 검증

| ID | 검증 | 실패 처리 |
|---|---|---|
| DATA-01 | `round`는 1 이상의 정수다. | 레코드 거부 |
| DATA-02 | `mainNumbers`는 정확히 6개다. | 레코드 거부 |
| DATA-03 | 본번호는 모두 1~45이고 서로 다르다. | 레코드 거부 |
| DATA-04 | `bonusNumber`는 1~45이며 본번호와 겹치지 않는다. | 레코드 거부 |
| DATA-05 | `drawDate`는 유효한 ISO 8601 날짜이며 미래 날짜가 아니다. | 레코드 거부 |
| DATA-06 | 본번호는 저장 전에 오름차순으로 정규화한다. | 정규화 후 저장 |
| DATA-07 | 동일 회차의 완전히 같은 레코드는 멱등 처리한다. | 변경 없음 |
| DATA-08 | 동일 회차의 기존 값과 다른 레코드는 정정 절차 없이는 적용하지 않는다. | 전체 갱신 중단 및 검토 상태 기록 |

추첨일이 통상 토요일이라는 사실은 경고 검증에 사용할 수 있지만, 일정 변경 가능성이 있으므로 날짜만으로 레코드를 거부하지 않는다.

### 7.2 데이터셋 검증

| ID | 검증 | 실패 처리 |
|---|---|---|
| SET-01 | manifest의 `latestDraw`가 데이터의 최대 회차와 같다. | 전체 갱신 거부 |
| SET-02 | 로컬 마지막 회차 다음부터 새 최대 회차까지 누락이 없다. | 전체 갱신 거부 |
| SET-03 | 회차와 날짜가 증가하는 방향으로 정렬된다. | 전체 갱신 거부 |
| SET-04 | snapshot 파일의 SHA-256이 manifest와 같다. | 전체 갱신 거부 |
| SET-05 | JSON 크기와 레코드 수가 안전 상한을 넘지 않는다. | 다운로드 또는 파싱 중단 |
| SET-06 | 모든 레코드가 레코드 검증을 통과한다. | 트랜잭션 롤백 |

### 7.3 애플리케이션 상태 검증

- 직전 회차 옵션은 로컬에서 검증된 최대 회차만 사용한다.
- 미출현 N회 옵션은 연속된 검증 회차가 N개 이상일 때만 활성화한다.
- 데이터가 오래됐더라도 기준 회차를 명시하고 기능을 사용할 수 있게 하되, 새 회차 확인 실패를 사용자에게 알린다.
- DB가 손상되면 앱 번들 스냅샷으로 복구한 뒤 원격 증분을 다시 적용한다.

## 9. 결정이 필요한 사항

### 결정 A: 데이터 권한 확인 경로

권장 순서:

1. 동행복권에 회차 결과의 앱 저장·표시·재배포와 자동 조회 가능 여부를 서면 문의한다.
2. 동시에 `smok95/lotto` 운영자에게 앱 사용·번들 재배포 허가 또는 라이선스 추가 가능 여부를 문의한다.
3. 둘 중 권한이 명확해진 출처를 원천 또는 교차 검증 출처로 선택한다.

### 결정 B: 허가 전 개발 범위

권장안은 데이터 인터페이스, 검증기, SQLite 저장소와 가짜 테스트 데이터까지 먼저 구현하는 것이다. 실제 네트워크 어댑터는 허가가 확인된 뒤 연결한다. 이렇게 하면 법적·운영 결정 때문에 나머지 개발이 멈추지 않는다.

### 결정 C: 갱신 운영 방식

원천에서 자동 수집이 허용되면 주 1회 수집 작업과 정적 피드 배포를 자동화한다. 자동 수집이 허용되지 않고 데이터 표시·재배포만 허용되면 관리자가 매주 결과를 확인하고 입력하는 작은 관리 작업을 사용한다.
